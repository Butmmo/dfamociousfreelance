# TPE — A Signal Layer Beyond Binary Tracking

*An additive system that sits on top of the existing binary "interacted once" tracking from `tpe.md` — doesn't replace it, doesn't gate it, doesn't punish. Addresses the gap named earlier: binary completion tells you someone opened the video, not whether it did anything.*

## Design constraints (stated up front)

1. The existing binary mechanic is untouched — one interaction still marks the week complete, exactly as it does now.
2. Nothing here is required. Skipping every part of this system leaves someone in exactly the same standing as today.
3. Nothing here is scored, ranked, or usable as grounds for a sanction — a direct extension of the existing "tracked, not punished" posture, not a workaround of it.
4. Nothing here creates a new place to remember to visit. Both pieces attach to touchpoints that already exist — the moment of marking a video complete, and the weekly BPS report.

## The two pieces

### 1. The Landing Check — a single tap, right at the moment of completion

The instant someone marks the week's video interacted-with, one optional, single-tap question appears — not a gate, not a delay; the binary mark has already fired by the time this shows up. Four options, deliberately symmetrical so there's no "correct" answer to perform:

- New to me
- Needed this reminder
- Already living this
- Didn't land this time

That symmetry matters more than it looks like it should. If the options skew positive, people learn to tap the flattering one and the signal becomes noise. "Didn't land this time" has to be exactly as safe to tap as any other option, or the whole layer collapses into a second compliance metric wearing a friendlier face.

Skipping it looks identical, everywhere, to answering it. No dot, no "incomplete" marker, no visual distinction. The moment skipping becomes visible, it becomes something people feel judged for skipping — which recreates the exact problem this is meant to solve.

**What it's for:** a participant's own private record of how the same topic has landed across cycles. "Order in Enterprise — Cycle 1: New to me. Cycle 3: Already living this." That's the "watching it again in month 14 lands differently" premise, made visible to the one person it should be visible to, instead of just assumed. Private by default.

### 2. The Application Note — one optional line, folded into the existing BPS report

Rather than a second text box in a second place, the elaboration lives inside the report that's already happening that same Monday: one optional line — "How does this week's TPE topic show up in your week?" No character minimum, no requirement, no visible difference in the report if it's left blank.

**What it's for:** the difference between resonance ("this landed") and application ("here's what I did with it"). The Landing Check captures the first; the Application Note captures the second — and it's the one that actually speaks to whether exposure turned into anything.

## Where the data goes — and where it explicitly doesn't

- **To the participant:** their own Landing Check history, across all twelve topics and every cycle they've completed. Nobody else's default view.
- **To a Rep or mentor — only inside an already-triggered support conversation, and only with the participant's knowledge that it's visible:** if someone's missed-week pattern already opens a support conversation under the existing policy, the mentor can see that person's own past notes as context — something to open with beyond "you've missed three weeks." This doesn't create a new trigger; it only makes an existing conversation better-informed. It should never be pulled up outside that context, and never used to justify escalating a conversation that wouldn't have already happened under the existing missed-week policy.
- **To whoever owns TPE content — aggregated by topic, never by person:** if "Didn't land this time" clusters heavily on one topic's video across cycles, that's a direct answer to the open question from before — whether the video content needs refreshing, or whether the "revisit lands differently" premise is actually holding up. This is the one place the data is used organizationally, and it's about the content, never the person who tapped it.

## Why this doesn't slide into punitive over time

Systems like this tend to drift — a signal meant as context quietly becomes a scorecard once someone in a review meeting asks "can we sort by this." Worth deciding, before launch, that the answer is no:

- No view exists that ranks or lists participants by their Landing Check answers.
- No view exists that shows an individual's answers to anyone but that individual, except inside the one already-triggered support-conversation flow above.
- "Didn't land this time" is never referenced in a support conversation as evidence of anything about the person — only ever as an opening into what would land better.
- None of this counts toward, or against, the binary completion. A participant who taps "didn't land" every week and never writes an Application Note has still completed TPE in full, every week, exactly as the existing system already defines completion.

## Before rolling this out everywhere

Tap-based prompts tend to get answered enthusiastically for the first few weeks and then trail off as novelty fades — that's normal, not a sign the system failed. Worth watching for during a pilot: does the Landing Check tap rate settle at some steady baseline (fine) or drop toward zero (a sign the prompt itself needs to change, not a sign to make it mandatory). Testing on a handful of topics or one cohort first would surface that before it's baked into all twelve weeks, universally.

---

Between this and the reflection idea in the curriculum doc, the two are really one system: the Landing Check is the tap-sized version, the BPS-report line is the version for anyone who wants to say more, and both report back into the same question the quarterly loop was already built to answer — whether this is actually landing, or just being watched.
